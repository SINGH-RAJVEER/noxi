# Verification and release specification

## Reference evidence

The copied CppNix 2.35.2 tests under [tests/nix/](../tests/nix/) are the initial test oracle. The snapshot contains language fixtures, shell tests, NixOS integration definitions, C++ unit test sources, and golden data. It matches tag `2.35.2` (commit `2c73b59`) object for object, and `just nix-snapshot-verify` checks that it stays unchanged. Preserve the copied data and record the upstream revision on each refresh. [Test snapshot](#test-snapshot)

The reference is the newest numbered CppNix release, 2.35.2, as of 2026-09-28. The previous snapshot came from an unreleased 2.36.0 development commit; [the test snapshot notes](#test-snapshot) records the change. Reference executables for fixture comparisons must be the 2.35.2 release.

The full official Nix repository can be fetched into the ignored `tests/nix-official/` checkout with `just nix-tests-update`; `tests/nix-official.lock` records its exact revision. It is used to run CppNix's own build and test suite. It currently names the same commit as the snapshot. Its results do not substitute for running the same cases against nix-rs. When `just nix-tests-update` moves it to a newer tag, do not mix that tag with the fixed 2.35.2 fixture expectations.

`crates/compat-tests/` already classifies the copied ATerm derivation fixtures against vendored `nix-compat`. Its expectation table names unsupported forms, including content-addressed and dynamic derivations. These classified gaps are useful progress markers, not passing compatibility cases.

Every copied fixture file has a classification in `crates/compat-tests/expectations/fixtures.txt`: `table` (a named test lists each file with its expected outcome), `pass`, `gap`, `anomaly`, `unrun`, or `ignore` for placeholders and generator scripts. `cargo nextest run -p nixrs-compat-tests --test fixture_inventory` walks the `src/*-tests/data` trees and `tests/` in the snapshot. It fails on these conditions:

- A file is unclassified.
- A pattern matches nothing.
- A `table` or `pass` entry names a test that does not refer to the fixture's directory.
- A `pass` entry's test does not name each file it claims.

On 2026-10-02 the 1,916 files were classified as follows:

- 1,140 are in per-file tables: 992 language, 58 worker-protocol, 20 path-info and nar-info, 18 derivation JSON, 17 store JSON, 14 derivation ATerm, 12 realisation and build-result, 6 derivation options, and 3 fetcher public-key files.
- 69 pass: the malformed NARs, six Git object files, the BLAKE3 and SHA-256 hash JSON files, 28 shared common and serve protocol files, and 25 additional serve value and handshake files.
- 13 are reference anomalies: `hash/sha512.json` contains a SHA-256 hash because CppNix 2.35.2's `HashJSON` test constructs SHA-256 for its `sha512` row; twelve old hash-based common and serve drv-output and realisation files are absent from the pinned C++ tests.
- 691 are unrun.
- 3 are ignored.

The seven shared primitive cases in each of the common and serve protocol fixture groups decode and re-encode byte for byte in `upstream_shared_protocols`. Their 28 binary and JSON files are classified as passing. The six remaining common-protocol drv-output and realisation files are stale: neither the pinned test nor the common codecs names those types, while worker and serve use their own versioned realisation codecs. An inventory test guards all 20 common files and confirms which stems the pinned C++ test names. These anomalies are not runtime passes or exclusions of realisation behavior from the compatibility gate. Store-reference, git hashing data, and every shell and NixOS test outside `lang` remain unrun.

`upstream_serve_protocol` checks 25 additional serve files against `nix_compat::cppnix_serve`: realisations at 2.8, build results at 2.2, 2.3, 2.6, 2.7, and 2.8, path info at 2.3 and 2.4, build options at 2.1, 2.2, 2.3, and 2.7, and the handshake. Values and writes match the copied JSON and binary fixtures; the reference only reads the old 2.6 build-result fixture, discarding old derivation hashes and signatures, so it is not a byte-round-trip claim. The 15 tests also check truncation, status validation, version negotiation, lexical store-path normalization, invalid path names, and the reference's permissive signature base64 decoding. Six stale hash-based serve files are anomalies, not evidence for current values. These codecs require `/nix/store` and UTF-8 names where the JSON models use strings; serve commands and actual engine pairings remain unrun.

`upstream_fetcher_public_key` checks the three copied fetcher key JSON fixtures. `simple` and `defaultType` read and write the same JSON, while `noRoundTrip` omits `type` on input and is read as `ssh-ed25519`; writing it makes the type explicit, as the 2.35.2 reference does. These source-fetcher declarations are separate from narinfo trusted verifying keys.

`upstream_git_objects` checks the copied Git blob and SHA-1/SHA-256 tree objects against `nix_compat::git` byte for byte, including their listed modes, names, and child hashes. It also rejects malformed object headers and tree entries. This covers the object encoding in the `git-hashing` fixture group; feature gating and source-accessor integration remain open.

`upstream_derivation_json` checks all 18 copied version-4 derivation and output JSON fixtures against the typed `cppnix_json::derivation` model. It checks output kinds, derivation names, output counts, structured-attribute presence, simple inputs, dynamic input children, and byte-identical JSON re-encoding. Fixed text, floating, impure, and dynamic-input cases require their respective experimental features at read time. This covers JSON representation; deriving output paths, interpreting structured attributes, and resolving dynamic dependencies remain separate work.

The ATerm parser in `nix-compat` accepts what 2.35.2's `parseDerivation` accepts:

- Outputs, input derivations, each input derivation's output names, input sources, and environment variables may appear in any order. A repeated output keeps the first entry (`emplace`); a repeated input derivation or environment key keeps the last (`insert_or_assign`); repeated output names and input sources collapse into sets. An input derivation may list no outputs. Serialising again writes the canonical sorted form, as CppNix does. `upstream_derivations.rs` checks that 2.35.2's anonymised `hello.drv` and `firefox.drv`, which list inputs sharing a digest out of path order, parse and canonicalise stably.
- Every string field decodes `\n`, `\r` and `\t`, and a backslash before any other byte yields that byte, including in store paths, output names and the platform. Raw newlines, carriage returns and tabs are accepted.
- An empty platform, builder or environment key, and input derivations whose name lacks `.drv`, parse; only derivations built from a `DerivationBuilder` reject them.
- Output names on input-addressed outputs and input derivation references retain non-UTF-8 bytes and parse even when they are empty, reserved, or contain characters that a new derivation cannot use. Fixed-output entries also retain their parsed name. The parser round-trips those names; `DerivationBuilder::build_unverified` still rejects invalid names. Local cases live in `crates/compat-tests/tests/derivation_parser_extensions.rs`.
- Platform, builder command, argument, and environment-key fields retain non-UTF-8 bytes while parsing and serialising ATerm. The same local test file checks a derivation containing non-UTF-8 bytes in all four fields. JSON output keeps its existing UTF-8 field format and returns an error when one of these fields cannot be represented there.

Hash derivation modulo follows 2.35.2's `insert_or_assign`: when two input derivations mask to the same hash, the output names of the later one in path order replace the earlier one's. `crates/compat-tests/tests/reference_hash_modulo.rs` checks this against derivations that the 2.35.2 reference wrote for CppNix issue #16307's graph, stored in `crates/compat-tests/fixtures/hash-modulo-collision/` with the expression that produced them. Merging the output names instead, as `master` does since the #16307 fix, fails that test.

The hash-modulo lookup now distinguishes a regular derivation's single digest from a fixed-output derivation's per-output digest map. A requested fixed output is replaced by its digest and the canonical `out` name; an empty requested set contributes no masked input, and a missing fixed output returns an error. Focused `nix-compat` tests cover the empty and missing-output cases, while the 2.35.2-generated graph checks the ordinary fixed-output path calculation. This is local evidence for these cases, not a complete fixed-output or derivation compatibility result.

Differences from 2.35.2 that remain:

- JSON output cannot represent non-UTF-8 output names and returns an error for them; ATerm retains the original bytes.

`crates/compat-tests/tests/upstream_derivation_options.rs` checks `nix-rs-build`'s derivation options against the six `derivation-options` JSON fixtures and CppNix 2.35.2's `derivation-advanced-attrs.cc`. Each fixture reads and writes byte for byte, and the four input-addressed ones also read as `DerivationOptions<StorePath>`. The four input-addressed advanced-attributes derivations, parsed from ATerm, produce the JSON of the fixture CppNix compares them with, along with the same required system features, substitution decision, and `uid-range` use. The four content-addressed ones do too, with `ca-derivations` enabled and placeholders mapped to the input outputs they stand for. Their floating outputs are not accepted by the ATerm parser yet, so their environment and inputs come from the equivalent derivation JSON fixtures. Without `ca-derivations`, a placeholder in a reference check is read as an output name and one in `exportReferencesGraph` is rejected as a path outside the store, as CppNix does. Nested placeholders for outputs of dynamic derivations are not supported, and these options are not yet applied to a build.

The masked-hash, `bad-ca-fixed-path.drv`, and `windows-store-dir.drv` fixtures are absent from 2.35.2, and their tests were removed with the refresh. These checks cover narrow format behavior, not complete derivation or store compatibility.

CppNix 2.35.2's JSON forms for store paths, content addresses, output specifications, and deriving paths live in `nix_compat::cppnix_json`, separate from the imported `serde` implementations, which follow Snix's conventions. `upstream_store_json` decodes each of the 17 fixtures, compares the values CppNix's unit tests construct, and re-encodes 14 of them byte for byte. The other 3 are nested deriving paths that 2.35.2 accepts only with `dynamic-derivations`. Both engines reject them by default, and nix-rs cannot yet accept them with the feature enabled. `cppnix_json::{PathInfo, NarInfo}` implement the path-info and narinfo JSON in all three format versions. `upstream_path_info_json` checks that each of the 20 fixtures decodes to the value CppNix's tests construct, including the self-referencing content-addressed path. It also checks that the 18 fixtures CppNix writes re-encode byte for byte. `cppnix_json` also covers `DrvOutput`, `Realisation`, `UnkeyedRealisation`, and `BuildResult`. `upstream_realisation_json` checks all 12 realisation and build-result fixtures. The checks cover the decoded values, the re-encoded bytes, and realisation fingerprints. They also check that signing a fingerprint with the test key from `realisation.cc` reproduces 2.35.2's ed25519 signatures exactly, and that those signatures verify.

`crates/compat-tests/tests/upstream_worker_protocol.rs` decodes the number of values stated by each JSON fixture at the version CppNix's test uses, and requires byte-identical re-encoding (decoding only, for the lossy reads CppNix also only reads). A count-bound read is necessary because an optional value at EOF may be interpreted as absent rather than as stream termination. It also checks decoded values against those the C++ test constructs. Three fixtures in the snapshot are not referenced by its C++ tests and are marked stale. Fixtures that need protocol feature negotiation, and the handshake, remain gaps.

The pinned nightly previously crashed while compiling the derive UI fixture for an enum whose version ranges leave gaps. `nix-compat-derive` now reports the first uncovered minor version before emitting the async match, preserving a compile-fail regression without treating the compiler crash as expected output. The full `just ci` command passes on the pinned development toolchain.

`crates/compat-tests/tests/upstream_nars.rs` checks that the Rust archive reader rejects the eight malformed NAR fixtures in 2.35.2 with their expected error categories, and that a stalled writer fails a copy. Although the copied release has no valid NAR fixture, `reference_nars` now checks four dumps from its pinned `nix-store --dump` binary. Both sync and async writers reproduce the bytes; both readers reproduce the recorded source nodes with small buffers, in 16 passing tests. The oracles cover binary regular files, executable files, symlinks, nested directories, empty nodes, and a non-UTF-8 filename. `crates/compat-tests/fixtures/nar-reference/provenance.json` records the executable, revision, payloads, commands, lengths, and SHA-256 digests. Run its sibling `generate.py` after `just reference` to print regenerated hex and provenance, or select a reference executable with `--reference`. Dumps use temporary source paths without opening the host store. Broader malformed/resource-limit behavior, store import/export, compression, and cache exchange remain open.

`crates/compat-tests/tests/upstream_lang.rs` runs all 467 `parse-*` and `eval-*` cases in the copied `tests/functional/lang/` directory. Each `eval-*` case runs nix-rs's `nix-instantiate` (the `nix-rs-commands` library entry point, with the store-aware builtins of `nix-rs-glue`) with the arguments `lang.sh` passes: `--eval --strict --show-trace` for `eval-fail` cases, `--eval --strict` for `eval-okay` cases, `--eval --xml --no-location --strict` for cases with an `.exp.xml` file, and each case's `.flags` as `lang.sh` applies them. A case whose arguments the command rejects is recorded as `unrun-flags`. `parse-*` cases only compile the file, because nix-rs has no printer for CppNix's `--parse` output yet. The runner reproduces `lang.sh`'s environment (including the `NIX_PATH` and `HOME` overrides that apply only to `eval-okay` cases), absolute file arguments, working directory, exit statuses, `/pwd` substitution, `.postprocess` script, and expected-file comparisons. Each case runs in a separate process with a 20-second timeout, so hangs and stack overflows are recorded rather than stopping the suite. The test fails if a file in the fixture directory is not a case, a companion of one, or a listed support file, or if a listed support file is missing. Every case's observed outcome is recorded in `crates/compat-tests/expectations/upstream-lang.txt`, with the evaluator's error code for failing cases, and any change in either direction fails the test. A case that still fails for a different reason, such as a newly implemented builtin exposing the next error, therefore also fails the test. After reviewing an intended change, run the test with `NIXRS_COMPAT_BLESS=1` to rewrite the table. Each run writes a JSON report with each case's command, outputs, exit codes, terminating signals, and timings to `target/tmp/upstream-lang-report.json`.

Until 2026-10-03 the runner reported its single test as ignored when nextest listed ignored tests, so `cargo nextest run` skipped it and only `cargo test` ran it. It also evaluated with the bare evaluator, without the store-aware builtins. Running the command instead moved 7 cases to `pass` (`autoargs`, `context`, `delayed-with`, `delayed-with-inherit`, `eq-derivations`, `path`, `substring-context`) and changed no passing case.

Each case runs with the configuration `common/init.sh` writes for functional tests outside NixOS (`nix-command` and `flakes` enabled, `show-trace`, and an `include` of `nix.conf.extra`), placed in the runner's scratch directory as `NIX_CONF_DIR`. Settings flags in `.flags` files, such as the lint settings and `--max-call-depth`, are accepted by the command, so those cases now run; the settings themselves are not acted on yet.

A recursive attribute set with a statically named `__overrides` attribute forces it while the set is built, rejects a non-set, adds its attributes to the result, and gives sibling references the overriding values, as CppNix does. Two differences from the reference remain. A plain `inherit a;` in such a set is bound before `__overrides` is known, so siblings still see the inherited value. An `__overrides` expression that refers to an attribute it overrides fails with infinite recursion where CppNix evaluates it. `nix-instantiate --eval` prints values like CppNix's `printAmbiguous`. Unevaluated values print as `<CODE>`, derivations as attribute sets, and a non-empty attribute set or list printed earlier in the same value as `«repeated»`. Lists are identified by the thunk they are reached through, the closest equivalent of CppNix's value cells. `builtins.trace` prints a string message as is and other values like CppNix's `ValuePrinter`: `«thunk»`, `«lambda NAME @ FILE:LINE:COLUMN»`, `«primop NAME»`, and `«repeated»`. It prints before forcing its second argument. Function names follow CppNix's `setName`. A function bound directly to a name, or returned directly by such a function, takes that name. `inherit (e) a b` evaluates `e` once. Positions of functions in `-E` expressions are offsets in the generated driver expression, not CppNix's `«string»` positions.

Integer addition, subtraction, multiplication, division, and negation now use checked arithmetic in both build profiles. Overflow returns an uncatchable evaluation error with the reference's operation and operand message instead of panicking or wrapping. Unary negation follows the reference's `0 - value` behavior. Division checks the divisor first for operators and builtins, including float negative zero and an invalid numerator with a zero divisor. All 43 focused `integer_arithmetic` tests in `eval/src/tests/one_offs.rs` pass under debug and release with `--no-default-features`. The copied overflow cases are still diagnostic mismatches, and only their four rows plus `eval-fail-div-3` were updated in the expectation table. The ad hoc checks at the top of `lang.sh`, covering `trace`, `warn`, `addErrorContext`, and `non-eval-fail-bad-drvPath.nix`, are not fixture files and remain unrun. `eval-okay-hash.exp` has no matching case upstream, so it is recorded as a reference anomaly.

`crates/compat-tests/tests/upstream_hashes.rs` checks BLAKE3 digests against three copied CppNix vectors and checks JSON encoding against its copied fixture. The library accepts BLAKE3 hashes, but the reference exposes them behind the `blake3-hashes` experimental feature. No nix-rs command or configuration layer enforces that feature gate yet, so BLAKE3 command compatibility remains unrun.

`crates/compat-tests/tests/reference_hash_formats.rs` records `nix hash convert` results from the pinned 2.35.2 binary for `abc` under MD5, SHA-1, SHA-256, SHA-512, and BLAKE3. It checks hex, nix32, base64, and SRI parsing and output, plus malformed digest rejection. A custom case found that 2.35.2 accepts uppercase hex; `nix-compat` now does too. The reference rejects BLAKE3 when `blake3-hashes` is disabled and accepts it when enabled. The Rust hash library has no feature setting, and nix-rs has no equivalent `nix hash convert` command yet, so that command-level gate remains open.

For each compatibility test, record the reference binary and nix-rs binary, platform, input revision, feature settings, store configuration, command or operation, expected result, actual result, and disposition. Tests that cannot yet run against nix-rs remain unrun. Tests that fail for a known reference issue still need an explicit compatibility decision; do not quietly rewrite expected output.

Map every applicable entry in the [reference inventory](reference-inventory.md) to acceptance cases and recorded results, including behavior without copied fixtures. Fixture classification is progress tracking, not a complete command, setting, builtin, fetcher, store-type, protocol, or library coverage claim. A reference-disabled case or fixture anomaly needs an explicit disposition and does not establish a nix-rs pass.

### Rust-core completion work

The active completion scope is the package-manager core in TODO sections 0 through 8. Lua, the installer and OS lifecycle, NixBox interfaces, and fleet execution remain outside this scope. Completion requires the pinned CppNix 2.35.2 qualification gates, not merely a passing workspace suite.

The current working tree adds writable evaluation through `EvaluatorStore::writable(root)` and single-derivation instantiation through `nix-instantiate --store 'local?root=ROOT'`. ROOT must be an existing absolute diverted directory. System roots and symlink-redirected store/state directories are rejected before opening the store. These checks are development safeguards, not an authorization boundary for untrusted concurrent users.

Ordinary `--eval` remains read-only. `--eval --read-write-mode` enables registration with an explicit diverted store. Read-only `--store` selections resolve logical `/nix/store` paths within the diversion without opening the writable database. Writable evaluation registers text, copied and filtered sources, and exact derivation ATerm bytes with their references; it does not build outputs. Source filters see logical paths, and expected source hashes are checked against captured bytes before those same bytes are registered.

`cargo test -p nix-rs-glue -p nix-rs-commands --locked --offline` passes 18 tests with one Nixpkgs test ignored because it needs `NIXRS_NIXPKGS`. Coverage includes dependency-output references, unchanged read-only behavior, diverted reads, logical filter paths, source hash checks, and single evaluation of a selected derivation. Build integration, import-from-derivation realization, persisted derivation hash lookup, recursive derivation selection, permanent command GC roots, and streaming source imports remain open. Captured imports currently buffer their contents in memory.

Evaluator regressions now cover adding string contexts to contextless strings, preserving existing contexts, weak message coercion for `abort` and `throw`, byte-oriented zero-width regex splitting, and non-UTF-8 `readDir` keys. Regex splitting advances by one byte, including inside multibyte input. The regex engine still differs from CppNix's POSIX engine, pattern strings remain UTF-8-only, and store-context validation and realization remain incomplete.

Flake-reference tests now cover forge formatting and selectors, empty refs, transport-query separation, Mercurial locations, explicit file/tarball types, relative paths, and repeated-parameter precedence. The `Mercurial` variant now includes a required `url` field. These are parsing/formatting fixes, not fetching, registry resolution, lockfile support, or full reference-format equivalence.

The async NAR reader now rejects reuse after abandoned children or exhausted directories, and poisons its reader tree after errors or partially polled directory-read cancellation. All three formerly ignored poisoning tests are enabled. All 16 reference NAR tests and both malformed-NAR compatibility tests pass. This does not establish general NAR resource limits or prevent direct reuse of an underlying reader outside the returned tree.

On 2026-10-03, `cargo nextest run --workspace --all-features` passed 2,631 tests with 4 skipped, with `NIXRS_REFERENCE_BIN` set to the pinned 2.35.2 build, and the doctests and formatting check passed. One of the skipped tests was the language runner, which nextest did not run until the listing fix described above. After that fix, the language table reported 111 passes out of 467 cases; its known gaps and the ignored network/Nixpkgs tests remain visible. Later review fixes received focused tests. No live host store or system service was replaced.

The next milestones are end-to-end realization and IFD, build scheduling and controls, store/cache/configuration completeness, the authorized daemon and client boundary, fetching/flakes/profiles and the command suite, then packaged NixOS/Home Manager qualification. None is complete solely because the local regression suite passes.

## Differential testing

The initial `differential-eval` runner compares ten pure expressions using `nix-instantiate --eval --strict --expr` and `nixrs eval --expr`, with an isolated temporary home and identical controlled environment. It clears inherited variables, sets empty `NIX_PATH` and `NIX_CONFIG`, points Nix's system and user configuration paths at temporary empty locations, uses `NIX_REMOTE=dummy://` and `NIX_STORE_DIR=/nix/store`, and passes the caller's `PATH` to both engines; the report records that path. Every version probe and case has a 20-second timeout, overrideable with `NIXRS_DIFF_TIMEOUT_MS`. A timeout is recorded and makes the case fail. The runner preserves a legacy command symlink because CppNix selects its command from the executable name. Run `just eval-compare /path/to/nix-instantiate /path/to/report.json` in the development shell. The JSON report contains each executable's path, resolved path, SHA-256 and version, the arguments, expressions, exit codes, terminating signals, stdout, stderr, timeout results, and mismatch disposition. Output that is not valid UTF-8 is also recorded as hex in `stdout_hex` or `stderr_hex`. A case where either engine is ended by a signal never matches, because a signal leaves no exit code and two different crashes with the same output would otherwise compare equal. Against the pinned reference, `just eval-compare-reference` matched 10/10 on 2026-09-28 using `nix-instantiate (Nix) 2.35.2` at `/nix/store/nskid3yq908g18x6cnvrk2hy96327f3f-nix-2.35.2`, the same path upstream's flake produces at `2c73b59`; the controlled runner also matched 10/10 locally on 2026-09-29. Ten pure expressions are development evidence, not language qualification. The flake preview package also built from a clean local Git clone, and its installed binary evaluated a nested value. This runner covers no store operations; its dummy store does not qualify a copied CppNix store or daemon behavior.

Compare both engines with identical inputs and isolated stores. The comparison must cover:

- Parse and evaluation results, strictness, warnings, errors, traces, source positions, string contexts, and import-from-derivation.
- Serialized derivations, input graphs, store paths, NAR contents, narinfo, cache signatures, and profile links.
- CLI flags, exit status, stdout, stderr, JSON, environment changes, and daemon protocol responses.
- Local and remote builds, sandbox restrictions, substitutions, cancellation, concurrent operations, corruption handling, and garbage collection.
- NixOS module evaluation, `system.build.toplevel`, activation actions, boot entries, generations, and rollback.
- Rebuild event semantics, rendered diagnostics, raw-log access, redaction, and machine-readable output as specified in [logging](logging.md).

Compare bytes where formats or command output require exactness. For build outputs whose content is intrinsically nondeterministic under the reference, compare behavior and invariants without incorrectly treating a changing output hash as proof of an engine defect. Keep these cases identified in the matrix.

The copied shell suite needs an isolated test store and compatible executables before it can validate nix-rs. The copied C++ tests are specifications for Rust ports and format fixtures; they are not Rust test results. NixOS tests require VM execution. [Test snapshot](#test-snapshot)

## Fleet tests

The later [distributed-computing specification](distributed-computing.md#acceptance-cases-and-release-evidence) requires project-owned multi-machine tests, not reinterpretation of copied remote-build fixtures as fleet qualification. ## Release gates

The package-manager MVP comes first. It can be described as a 100% drop-in replacement only when the CppNix 2.35.2 compatibility matrix is complete for its declared existing-system target and every applicable command, setting, format, build, store, daemon, cache, and public library interface passes. This includes rebuilding a supported existing NixOS installation with nix-rs, existing-store interoperation, return to the reference implementation, and a safe installation and rollback procedure for the package manager. Publish the tested binaries, source revisions, licenses, reports, signatures, and known limits with the release. OS installation, recovery-media, TUI, and GUI rows remain separate later gates and do not weaken this first compatibility claim.

Run applicable qualification against the exact packaged release-profile executables and libraries. Record artifact hashes and build inputs in the reports; debug-profile workspace tests alone cannot qualify release artifacts. If an artifact changes, rerun affected qualification before publishing it. Additional Rust crates may be published separately, but stable Rust APIs are not part of the CppNix drop-in contract.

The later OS release additionally requires:

1. The installed OS builds and activates its next generation using nix-rs, with no CppNix dependency for normal maintenance.
2. Installer, update, rollback, and recovery workflows pass on every advertised platform.
3. CLI, TUI, and GPUI-based NixBox GUI operations pass their shared behavior and accessibility tests.

A later release advertising fleet or distributed-computing support must additionally pass the fleet security, lifecycle, service-topology, partial-recovery, and measured-scale gates for every advertised support combination. Single-machine OS qualification and CppNix compatibility cannot substitute for those results, and fleet results cannot substitute for either earlier gate.

If a gate is open, continue development and report the specific gap. No release can claim behavior that its qualification evidence does not cover.

The ATerm parser in `nix-compat` accepts what 2.35.2's `parseDerivation` accepts:

- Outputs, input derivations, each input derivation's output names, input sources, and environment variables may appear in any order. A repeated output keeps the first entry (`emplace`); a repeated input derivation or environment key keeps the last (`insert_or_assign`); repeated output names and input sources collapse into sets. An input derivation may list no outputs. Serialising again writes the canonical sorted form, as CppNix does. `upstream_derivations.rs` checks that 2.35.2's anonymised `hello.drv` and `firefox.drv`, which list inputs sharing a digest out of path order, parse and canonicalise stably.
- Every string field decodes `\n`, `\r` and `\t`, and a backslash before any other byte yields that byte, including in store paths, output names and the platform. Raw newlines, carriage returns and tabs are accepted.
- An empty platform, builder or environment key, and input derivations whose name lacks `.drv`, parse; only derivations built from a `DerivationBuilder` reject them.
- Output names on input-addressed outputs and input derivation references retain non-UTF-8 bytes and parse even when they are empty or contain characters that a new derivation cannot use. `drv` is an ordinary output name, as in 2.35.2. Fixed-output entries also retain their parsed name. The parser round-trips those names; `DerivationBuilder::build_unverified` still rejects invalid names. Local cases live in `crates/compat-tests/tests/derivation_parser_extensions.rs`.
- Platform, builder command, argument, and environment-key fields retain non-UTF-8 bytes while parsing and serialising ATerm. The same local test file checks a derivation containing non-UTF-8 bytes in all four fields. JSON output keeps its existing UTF-8 field format and returns an error when one of these fields cannot be represented there.

Hash derivation modulo follows 2.35.2's `insert_or_assign`: when two input derivations mask to the same hash, the output names of the later one in path order replace the earlier one's. `crates/compat-tests/tests/reference_hash_modulo.rs` checks this against derivations that the 2.35.2 reference wrote for CppNix issue #16307's graph, stored in `crates/compat-tests/fixtures/hash-modulo-collision/` with the expression that produced them. Merging the output names instead, as `master` does since the #16307 fix, fails that test.

The hash-modulo lookup now distinguishes a regular derivation's single digest from a fixed-output derivation's per-output digest map. A requested fixed output is replaced by its digest and the canonical `out` name; an empty requested set contributes no masked input, and a missing fixed output returns an error. Focused `nix-compat` tests cover the empty and missing-output cases, while the 2.35.2-generated graph checks the ordinary fixed-output path calculation. This is local evidence for these cases, not a complete fixed-output or derivation compatibility result.

Evaluation errors are rendered by `noxi_eval::diagnostics`, a port of CppNix's `showErrorInfo`, `printCodeLines` and `printTrace` (`libutil/error.cc`) and of the line splitting and byte-column positions of `position.cc` and `pos-table.cc`. Its unit tests compare rendered errors byte for byte with three `.err.exp` files, including duplicate-frame folding and suggestions. `nix-instantiate`, and the legacy commands that evaluate through it, print errors this way; `NOXI_DIAGNOSTICS=codespan` selects the earlier annotated source renderer. Each error carries a flat CppNix-style trace built from the VM's frame stack: `while calling the 'NAME' builtin` at a call in Nix code (without a position when another builtin makes the call), and `from call site` and `while calling 'NAME'`/`anonymous lambda` for function bodies under `show-trace`. Frames of the command's generated driver expression are left out. Builtin arguments are forced first to last and checked as CppNix's primops check them: the builtin macro expands a table of each primop's `forceList`, `forceFunction` and similar calls, with their type errors and `while evaluating the first argument passed to builtins.X` frames, in CppNix's order (`map`, `filter` and `sort` check the list first and skip the function check for an empty list). Return values and list elements carry the corresponding frames for `all`, `any`, `filter`, `partition`, `concatMap`, `concatLists`, `catAttrs` and `groupBy`, and the arithmetic builtins check integer or float operands as CppNix does. Deep forcing for `--strict` and `builtins.deepSeq` adds `while evaluating the attribute 'NAME'` frames at attribute definitions and `while evaluating list element at index N` frames. A `throw` or other catchable error records its trace where it is raised, because catchable errors propagate as values after their frames are gone; inside `builtins.tryEval` nothing is recorded. A catchable error memoised in a thunk and forced again elsewhere still shows the trace of its first raise, where CppNix re-evaluates the thunk. Because the CppNix format does not print noxi's error codes, each child process writes the codes of the errors it printed to a scratch file, and the runner reads the table's code column from there.

### Sandbox path targets, 2026-11-25

`sandbox-paths` targets could reach the host. At `da3e6d7c` the sandbox setup created mount points by path before `pivot_root`, following symlinks. With `/a=LINK` and `/a/new=FILE`, where `LINK` is a symlink to a host directory, it created `new` in that directory on the host; a directory source created a directory there and a symlink source a symlink. A symlink inside a bound directory had the same effect, so somebody who may write to a bound directory could redirect a configured target below it. The process that creates them has the host identity of the building process, root in a daemon run as root, and the mounts themselves stay in the build's private mount namespace. Existing host files were not overwritten (`O_EXCL`), and `..` was already refused. Only trusted users can set `sandbox-paths`, so an untrusted client needs such a configuration to exist.

noxi now follows the reference's `doBind`: every component is opened with `O_NOFOLLOW` relative to the chroot's directory descriptor, `..` cannot rise above it, and sources and targets are attached by descriptor with `open_tree` and `move_mount`. `reference_sandbox_paths` compares 121 settings with the reference, including the messages, and checks that the host tree is unchanged: targets below symlinks, also in bound directories; `..`, `.`, empty and relative targets; targets over `/etc`, `/dev`, `/proc`, `/tmp`, `/build`, the store and `real-root`; and optional paths. `linux-sandbox` passes.

Remaining, as in the reference: a directory bound to `/etc` is made read-only on the host when the building process owns it; a symlink bound to `/proc` or `/dev` directs the sandbox's own mounts, in its private namespace; and a target below a bound directory creates missing components in that directory. When one setting without `extra-` gives two sources for one target, the reference uses the last in byte order and noxi the first. The checks ran unprivileged in user namespaces; a root daemon with build users needs a VM.

### Builtin builders in the sandbox, 2026-11-25

At `da3e6d7c` the builtin builders ran in the process that builds. `builtin:fetchurl` refused `file:` URLs for that reason, but `builtin:unpack-channel` and `builtin:buildenv` followed any path in their attributes, so a derivation could make a daemon read a tarball or list a directory that the builder could not. All three now run in the forked builder process after the sandbox is set up and the user is switched. `reference_fetchurl` compares them with the reference through loopback HTTP and HTTPS servers: `file:` URLs of visible and hidden files, `netrc` lookup including redirects and credentials in URLs, `ssl-cert-file` from the setting and the environment, mirrors, unpacking, executables, retries, HTTP errors, `timeout`, `max-silent-time` and `stalled-download-timeout`. `does_not_inherit_privileges_or_the_environment` reads `/proc/self/status` and `/proc/self/environ` through a `file:` URL.

Three things the reference exposes to a derivation are withheld, because matching them would be harmful. Each was observed with the pinned reference and an impure derivation:

- `file:///build/netrc` returns the contents of `netrc-file`, which the reference copies into the build directory. noxi keeps them in memory, so that URL fails.
- `file:///proc/self/environ` returned the environment of the process that builds, in a build without build users. noxi clears it, except for the proxy variables.

Remaining differences: only HTTP, HTTPS and `file:` URLs are supported; an interrupted body is not resumed with a range request; certificates are checked by rustls, which for example refuses a CA certificate as the server's own; and proxies are chosen by ureq's rules rather than curl's. The checks ran as an ordinary user. A root daemon switching to build users, and `sandbox = false` with build users, need a VM.

## Release gates

The package-manager MVP comes first. It can be described as a 100% drop-in replacement only when the CppNix 2.35.2 compatibility matrix is complete for its declared existing-system target and every applicable command, setting, format, build, store, daemon, cache, and public library interface passes. ### Intentionally excluded from byte comparison

These differ between runs of the same engine, or depend on a library the format does not specify, so the tests mask or skip them rather than compare them:

- `registrationTime` in `nix path-info --json`: the time the path was registered. `reference_substitute` and `reference_build` remove it before comparing; `reference_store` and `reference_store_round_trip` compare it only against the value the same store recorded.
- `ultimate` follows how a path entered the store (built locally or substituted), so tests compare it against the expected origin rather than across engines.
- Compressed NAR bytes, and with them the narinfo `URL`, `FileHash` and `FileSize` of compressed uploads: they depend on the compressor library, its version and level. `reference_substitute` checks that the reference accepts noxi's gzip, bzip2 and zstd uploads instead of comparing bytes; uncompressed narinfo is compared byte for byte.
- Build-result `startTime`, `stopTime` and `timesBuilt` are wall-clock and history values; the copied fixtures fix them and live builds do not compare them.
- The text of nlohmann JSON parse errors. An invalid `__json` attribute fails in both engines with the same `cannot process __json attribute: ` prefix, but noxi reports serde_json's description of the error.

### Remaining differences

- Floating-point digits: nlohmann takes digits from Grisu2, which can emit a longer round-trip form than the shortest one Rust prints; such values would differ in `__json` and in the derivation path. No recorded case triggers this.
- Git-hashed fixed outputs (`git:` with a hash) and text-hashed fixed outputs other than SHA-256 parse in CppNix with their features enabled, but `CAHash` cannot hold them; `from_aterm` reports them as unsupported.
- Non-UTF-8 strings in a derivation are accepted by CppNix; the JSON-based full model holds text only and reports them as unsupported. `UnverifiedDerivation` still reads them for the default-feature formats.
- `realisation::DrvOutput` still prints and parses the pre-2.35 `<hash>!<output>` form; 2.35.2 keys realisations by derivation path, which `cppnix_json::DrvOutput` implements.
- Nested derived paths (`drv^out^bin`) need `dynamic-derivations` in CppNix, which reports a feature error; `DerivedPath` rejects them as an invalid store path name. Under the qualified `nix-command flakes` profile both reject the input, with different messages.
- `noxi-store`'s `BuildDerivation` still reads floating and experimental outputs with its own output-tuple pre-parser and keeps the rest as `UnverifiedDerivation`, rather than using `from_aterm`. It copies `__json` as raw bytes and formats no floats, so it does not affect the float evidence above. Moving it to `from_aterm` is not a contained change: the store and builder use `UnverifiedDerivation` throughout, and `from_aterm` cannot hold non-UTF-8 strings or the Git and non-SHA-256 text outputs this reader accepts.

## Remote builders, 2026-11-26

noxi builds on other machines as CppNix 2.35.2 does. The worker offers each derivation to the `build-hook` before building it locally, unless the derivation prefers a local build; checks and repairs stay local. `nix __build-remote` is the default hook. The hook is started directly with an argument vector, in its own session, with the reference's descriptors 4 and 5, and is sent every setting whose experimental feature is enabled, as `GlobalConfig::getSettings` gives them. The default hook is started even when no machine is configured, as in the reference, and declines permanently; it is skipped only if no `nix` is installed next to the running program. Goals reach the hook and the local build slots in a fixed order: each gets a turn when it is taken, and a goal waiting for a slot gets a new one, in goal key order, when a slot is free. The reference's first build is the same. After it, the reference's order is not defined by the derivations: `Worker::wantingToBuild` is a `WeakGoals` set ordered by `std::owner_less`, the addresses of the goals' control blocks. With `-j1` and five independent leaves, 2.35.2 started them a, b, c, d, e in one environment, a, c, b, e, d in another and a, e, d, c, b in a third, so only the first build and the set of builds are compared. SIGINT, SIGTERM and SIGHUP now interrupt a command as in the reference, also when the parent ignored them: builds stop, the build hooks are signalled so their machines stop building, and the command ends with `error: interrupted by the user` and status 1. Before, a noxi command ignored an inherited SIGINT, and under a terminal one died without stopping its builds. Machines can be local stores, `unix://` daemons, `ssh://` stores (`nix-store --serve --write`) and `ssh-ng://` daemons.

`crates/noxi-commands/tests/reference_build_remote.rs` (store tier) runs each case with both engines in one directory, one after the other, and compares exit status, standard output and standard error. No host is contacted: `ssh` is a script on `PATH` that records its arguments and runs the command on a chroot store of this machine. Its 25 tests cover (`daemons_build_on_machines` and `serve_and_daemon_machines_are_interchangeable` run in the daemon tier, the others in the store tier):

- Machine choice: system types, supported and mandatory features, `preferLocalBuild`, `-j0` and `-j1`, `--builders ''`, `--build-hook ''`, machines files, `@file`, `NIX_REMOTE_SYSTEMS`, malformed specifications, slots locked by another process (both engines name the lock files the same way), load relative to speed factor, and postponing while a machine is busy.
- Building: local machines, `ssh://` and `ssh-ng://`; multiple outputs, structured attributes, fixed outputs, quoting in derivation fields, phases, `nix log`, `post-build-hook`, `builders-use-substitutes`, content-addressed outputs with their realisations, and a daemon building its client's derivations on its own machines.
- Failures: builder failures with `--keep-failed`, wrong fixed-output hashes, `max-silent-time`, `timeout` and `max-build-log-size` on the machine and locally, unreachable hosts (the machine is disabled and the build falls back or is rejected), and a host that prints a banner instead of `started`.
- The hook protocol: the settings stream and the `try` request byte for byte, the arguments and working directory, JSON messages, and custom hooks that reply nonsense, die, accept without a machine name, or do not exist.

Each step has a hard timeout and kills what is left.
